# Testing the new C++ in PCSX2 (halfcpp) and bugs found

(Docs index in `CLAUDE.md`.) halfcpp was the first way to run the equivalents; the intended path is now the guinea-pig runtime (`NATIVO.md`, "Guinea-pig runtime", incomplete). What stays here is how to build the ELF and the lessons.

## How to build and run halfcpp
- The normal build's ROM is identical to retail (equivalents stay as `INCLUDE_ASM`). `sh tools/wsl/build_nm.sh` (WSL) compiles a copy in `~/wotm_nm` with `-DNON_MATCHING` and writes `build/pcsx2_test/SCUS_971.97_halfcpp.elf` (all the equivalents) and `..._control_matching.elf` (control). Both with `p_paddr = p_vaddr` (PCSX2 loads by `p_paddr`). Variants with a subset of TUs/functions: arguments to `build_nm.sh` (e.g. `a_update` with only `Monster::update`).
- Running: `pcsx2-qt.exe -elf build\pcsx2_test\SCUS_971.97_halfcpp.elf -- "ISO\...iso"`; automated: `powershell tools/pcsx2_auto/play.ps1 halfcpp 60` (switches the bindings to keyboard, plays the menu up to the stage, watches the log and restores the `.ini` with `emu.ps1 stop`; `-pause` presses START and photographs the dialog; `play.ps1 <elf> <n> <file>` dumps the RAM). The PCSX2 log is in `~/Documents/PCSX2/logs/emulog.txt`: `Unrecognized op`/`executing data` = jumped into data; `Vif0: Unknown VifCmd` = wrong data; errors in dialogs show up as `ReportErrorAsync`.
- **Layout** (`tools/gen_nm_ld.py`): the normal linker script stacks the pieces, and any equivalent of a different size shifts the data after it (misaligned DMA buffers, which is what broke the first test). The generated script pins every piece that didn't grow at its retail address and sends the ones that grew to `.nm_extra`, after the bss. Limit: it only pins the start of each piece; raw addresses into a shifted piece are wrong (`undefined_*_nm.txt` relative to the symbol; `nm_fix_data.py` for function tables in `.short`; see "Guinea-pig runtime").
- **Heap**: `.nm_extra` sat right after the bss, where the game's heap starts, and after a stage loads the whole RAM is in use (DMA overwrote the start of `takeHit`; symptom `executing data`). `patch_paddr.py --heap` (called by `build_nm.sh`) pushes the start of the heap past `.nm_extra` in two places: the crt0's `SetupHeap` call and `heap_ptr` in `libkernl/glue.data` (0x6E5D2C). `NM_HEAP=0x8E0000` puts the heap in the same place in both builds, so `ramdiff.py` can compare addresses.
- `CrushLevel` and `Monster` are compiled with `-G0` in the NM build (the new code's strings don't fit in `.sdata`). `hierDmaHandler` needs the `hierFlushObjQ` prototype in `hieri.cpp` when it is the only one that is `NON_MATCHING`.
- The full halfcpp enters the stage and runs a whole match ("AI WINS"). If a variant hangs with "executing data", compare the EE RAM against the ELF before suspecting the function (rule from `CLAUDE.md`).

## Behavior bugs found while playing halfcpp
Symptoms from the owner's test: ground vehicles without the green glow, and ◯ doesn't pick them up; pedestrians walking in single file; some buildings can be walked through. Causes, reading the equivalents against the asm:
- **`PathNode` had 0x40 bytes, retail uses 0x30** (4-byte links starting at 0x12, there are 7, not 9): `PathNet::getRandNode/getClosestNode` indexed the wrong nodes -> pedestrians (and cars, which follow the PathNet) in single file. There is a `typedef char PathNodeSizeCheck[...]`.
- `AiBrain`: the empty base class `AiActionGroup` takes 1 byte in gcc 2.95 and pushed `f_AAC` to 0xAB0 (retail 0xAAC). No inheritance now.
- `AiGrappleAttack::updateAction`: with `matchMode` 0/1 retail picks `heavyPunch` at random (ours called `toss`). Found by `tools/nm_calls.py`.
- `Monster::isIdle`: the last test was inverted (retail returns 1 when `t < state[2]`); only the camera uses it.
- **`Interactives::addInteractive` written as `void`**, but the retail callers (`CarPickup::initAfterDbLoad`, `HeliPickup`, `Destructible`...) use `$v0` (the slot index) as the id in the `hierhead`. The leftover `$v0` was index+1, so every `getInteractive(idx)` returned the neighbor: that breaks `getClosestPickup` (glow and ◯), the thrown-back ball and continuous damage on buildings. `tools/nm_retvals.py` scans the `void` equivalents whose return value is consumed.
- `Monster::update`: `sb` at `m_x6874+0xC` and `f5C` as a byte.
- **Lesson:** "untuned" with many differing words can hide a layout/semantic error, and the difftest caught none of these (random state, stubbed callees). Hence `nm_audit.py` (offsets and immediates, NM ELF x retail), `nm_calls.py` (call sequence), `nm_retvals.py` and `ramdiff.py` (two EE RAM dumps at the same point: equal pickup lists, `Interactives`, `ColGrid` and pools = the stage setup is right, the defect is dynamic). All of that runs together in `tools/verify_tu.py`.
- How to find a defect of this kind again: dump the RAM with the game paused (`ramdump.py`), and write a scratch script that reproduces the retail computation from the dump (that is how `getClosestPickup` was found).
- difftest with structured state: `--init '<python>'` (W/W16/W8/THIS/ARENA/STUB); `Monster::update` needs `m_state` with a vtable and still runs into writes outside the map.
